# P0 开发复盘

## 项目结果

P0 完成了一个本地 CLI 结构化内容生成器，验证 Python 项目结构、虚拟环境、固定依赖、环境变量、HTTP API、Pydantic、JSON Schema、错误处理、有限重试、自动测试和固定评估。

最终证据：

- CPython `3.14.3` 项目本地 `.venv`。
- `89` 个自动测试通过。
- `pip check` 通过。
- 10 条固定评估样本。
- `improved_v2` Schema 通过率 `100%`。
- 人工确认事实支持率 `97.3%`（109/112）。

## 最难的问题

最难的问题不是生成合法 JSON，而是限制模型只能使用输入材料。

`improved_v1` 已达到 `100%` Schema 通过率，但事实支持率只有 `52.2%`。模型补充了看似正确的 Transformer、虚拟环境、HTTP、LoRA 和安全知识。这证明结构正确和事实受支持是两个独立指标。

## 采取的改进

`improved_v2` 增加：

- 每个事实项必须对应材料原句或保守改写。
- 禁止补充材料外定义、机制、原因、影响、命令、数字和产品名。
- `common_mistakes` 没有材料依据时使用空列表。
- `missing_information` 只记录明确缺失或解决矛盾必需的信息。
- 默认 `example=null`。
- 输出前执行逐项材料证据检查。

相同模型、参数和固定评估集复测后，事实支持率从 `52.2%` 提高到 `97.3%`。

## 做得好的地方

- 先定义 PRD 和架构，再实现代码。
- Pydantic 模型作为 JSON Schema 唯一真源。
- 供应商适配器与业务逻辑分离。
- 自动测试全部使用假客户端，不产生费用。
- 超时、网络、HTTP、非法 JSON 和 Schema 错误有稳定分类。
- 真实评估前先做单请求冒烟。
- 保留每个 Prompt 和评估结果，优化过程可复现。
- API Key 未进入 Git 或评估结果。

## 仍需改进

- `improved_v2` 漏掉 3 个预期缺失信息和 1 个提示注入覆盖点。
- 默认不生成示例牺牲了部分教学体验。
- 事实评分仍依赖人工。
- 评估脚本未记录 token、供应商请求次数和精确费用。
- 尚未验证其他操作系统。
- 未选择公开许可证。

## 如果重做一次

- 在输入模型中增加明确的示例策略，而不是让 Prompt 自行判断。
- 为评估结果增加必覆盖内容和缺失信息行为的结构化人工字段。
- 在不保存敏感响应的前提下记录 token 用量、请求次数和供应商 request ID。
- 把“事实支持”和“内容覆盖”设为两个独立验收指标。

## 能向面试官解释的取舍

- 为什么 P0 使用 CLI，而不是 Web 服务。
- 为什么直接使用 HTTPX，而不是安装供应商 SDK。
- 为什么只重试暂时性传输错误。
- 为什么 Schema 通过率不能替代事实支持率。
- 为什么保留失败的 Prompt 版本和评估结果。
- 为什么 `improved_v2` 优先事实安全，接受示例数量降为零。
