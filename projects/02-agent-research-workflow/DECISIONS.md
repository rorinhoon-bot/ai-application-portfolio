# DECISIONS

## D-001：先做单工作流

- 状态：accepted
- 决定：先使用 LangGraph 显式状态图，不默认采用多智能体。
- 原因：需要先证明多角色能带来超过复杂度和成本的收益。

## D-002：选择 AI 应用技术选型研究报告

- 状态：accepted
- 日期：2026-07-29
- 决定：P2 首版为 2～4 个候选方案生成带证据的 AI 应用技术选型研究报告。
- 原因：该场景能自然展示规划、检索、Tool Calling、审校、Human-in-the-loop、恢复和幂等；范围与评估比实时竞品研究更可控。
- 备选：开源库升级迁移报告、AI 产品竞品与市场研究简报。
- 代价：固定快照不能保证实时性；评价维度和权重仍需人工确认。

## D-003：首版使用受控固定资料，不开放任意联网搜索

- 状态：accepted
- 日期：2026-07-29
- 决定：首版只读取经批准、版本化并带哈希的公开资料快照；不提供任意 URL 抓取工具。
- 原因：保证普通测试离线、评估可复现，并降低提示注入、许可、隐私和网页变化风险。
- 边界：当前阶段不下载资料。下载前另交来源清单、许可、大小、保存位置和校验方案。

## D-004：设置两个强制 Human-in-the-loop 暂停点

- 状态：accepted
- 日期：2026-07-29
- 决定：研究需求和范围必须先由人确认；最终报告必须按具体 revision 与内容哈希批准后才能导出。
- 原因：防止系统自行扩大研究范围、消耗预算或把未审查草稿当成最终结论。
- 结果：等待人工是显式 `NEEDS_HUMAN` 状态；旧批准不能授权修改后的报告。

## D-005：Tool Calling 只开放只读检索和纯计算

- 状态：accepted
- 日期：2026-07-29
- 决定：首版允许 `search_sources`、`read_source` 和 `calculate_comparison`；最终导出由程序控制，不作为模型工具。
- 原因：仍能展示真实 Tool Calling 循环，同时把 URL、路径、命令和写操作排除在模型权限外。
- 结果：工具调用必须经过名称 allowlist、Schema、业务范围、权限和预算校验。

## D-006：所有自动循环设置硬上限

- 状态：accepted
- 日期：2026-07-29
- 决定：工具初次调用后最多重试 2 次；检索最多 2 轮；自动审校修改最多 2 轮；人工退回最多 2 次；结构化输出最多再生成 1 次。
- 原因：避免无限循环、隐藏费用和不可解释的长任务。
- 边界：调用总预算优先于各局部上限；预算耗尽立即停止。

## D-007：使用 checkpoint 恢复和内容寻址的幂等导出

- 状态：accepted
- 日期：2026-07-29
- 决定：节点成功后和人工暂停前保存版本化 checkpoint；最终 `artifact_id` 绑定 `run_id`、批准 revision、内容哈希和格式。
- 原因：证明暂停恢复可靠，并防止节点重放或重复确认产生重复外部副作用。
- 结果：同一制品重复导出返回 `UNCHANGED`；同 ID 不同内容返回冲突，不覆盖。
- 结果：本地 checkpointer 固定为 `langgraph-checkpoint-sqlite==3.1.0`。

## D-008：P2 与 P1 保持工程隔离

- 状态：accepted
- 日期：2026-07-29
- 决定：P2 使用独立 `.venv`、独立状态和工具合同；不复制 P1 代码，不导入 P1 内部模块。
- 原因：P1 可作为质量参考，但直接耦合会隐藏 P2 的独立实现证据并增加环境冲突。
- 可选后续：若确需复用 P1 检索能力，只通过版本化只读适配器，并先记录依赖、数据和评估边界。

## D-009：内容质量与工作流可靠性分层评估

- 状态：accepted
- 日期：2026-07-29
- 决定：固定评估同时覆盖报告质量，以及路由、重试、停止、人工暂停、恢复和幂等。
- 原因：漂亮报告不能证明工作流可靠；只测状态机也不能证明研究结果有用。
- 目标：首批至少 12 个固定案例，覆盖成功、失败和人工介入三类路径。

## D-010：首个实现阶段使用最小直接依赖

- 状态：accepted
- 日期：2026-07-29
- 决定：直接固定 `langgraph==1.2.9`、`langgraph-checkpoint-sqlite==3.1.0`、`pydantic==2.13.4`、`pydantic-settings==2.14.2` 和 `pytest==9.1.1`。
- 原因：这些包足以实现显式图、checkpoint、严格合同、配置和离线测试；模型 SDK、向量库、UI 和 LangChain 当前不必要。
- 兼容边界：先在 P2 独立 CPython 3.14.3 `.venv` 做 wheel-only dry-run；完整传递依赖锁定后才安装。

## D-011：LangGraph 选择 1.2.9，不追随一天前发布的 1.2.10

- 状态：accepted
- 日期：2026-07-29
- 决定：首版固定 `langgraph==1.2.9`。
- 原因：1.2.9 已发布 19 天；1.2.10 于 2026-07-28 发布。当前没有必须升级到 1.2.10 的已确认修复需求，先降低新补丁回归风险。
- 安全：1.2.9 高于已知 checkpoint 反序列化修复版本 1.0.10。
- 后续：升级必须使用同一固定评估集回归，不直接改浮动版本。

## D-012：SQLite checkpoint 启用严格反序列化

- 状态：accepted
- 日期：2026-07-29
- 决定：使用 `langgraph-checkpoint-sqlite==3.1.0`，并设置 `LANGGRAPH_STRICT_MSGPACK=true`；不允许用户控制 metadata filter key。
- 原因：3.1.0 高于 SQL 注入修复版本 3.0.1；严格 msgpack 可缩小 checkpoint 数据库被篡改后的反序列化风险。
- 边界：checkpoint 只保存项目自有基础类型和严格验证数据，不启用 pickle fallback。

## D-013：首批评估只使用原创虚构资料

- 状态：accepted
- 日期：2026-07-29
- 决定：先创建 10 个原创资料文件和 12 个固定工作流案例，不下载真实框架文档。
- 原因：先隔离验证状态、路由、重试、暂停、恢复、幂等和提示注入边界，避免网页变化、真实检索和模型随机性混入。
- 结果：首批不需要向量库、Embedding、付费数据或网络；真实技术资料另建评估版本。

## D-014：接受必要传递依赖，但不启用外部追踪

- 状态：accepted
- 日期：2026-07-29
- 决定：接受 `langgraph==1.2.9` 解析出的 `langchain-core==1.5.2`、`langsmith==0.10.11` 等必要传递包；不启用 LangSmith tracing，不配置 LangSmith Key。
- 原因：这些包是 LangGraph 当前依赖图的一部分，不能在保持受支持安装的同时安全删去；安装包不等于授权外部服务调用。
- 验证：45 个锁定包与实际环境完全一致；离线状态图和 SQLite 恢复验证无网络调用。

## D-015：修正 P2 虚拟环境磁盘边界

- 状态：accepted
- 日期：2026-07-29
- 决定：P2 `.venv` 稳态磁盘边界从估算 50 MiB 修正为 65 MiB。
- 原因：45 个 wheel 压缩后仅 8.48 MiB，但安装展开和 `.pyc` 后为 62.66 MiB；未新增依赖。
- 处理：删除只含 45 个 wheel 的临时 wheelhouse，环境从 71.13 MiB 降到 62.66 MiB。
- 边界：后续新增依赖使环境超过 65 MiB 时重新评估。

## D-016：以内容寻址快照冻结 `workflow-v1`

- 状态：accepted
- 日期：2026-07-29
- 决定：10 个原创来源、12 个工作流案例和金标准共同绑定来源快照 `0e73ca7de985cdccb9295252fe2e7f3b2725183681a0576db2c7fb0838b44e3c`。
- 原因：先固定输入和预期，再实现状态图，避免根据实现结果回改评估。
- 结果：加载器严格校验路径、成员、字节数、哈希、证据 ID、候选 ID 和跨文件快照；任一不一致整批失败。
- 边界：修正 v1 资料必须创建新快照；看到运行基线后不得静默覆盖金标准。

## D-017：失败案例允许空推荐集合

- 状态：accepted
- 日期：2026-07-29
- 决定：需求不完整、证据不足或确定性工具失败时，金标准的 `allowed_candidates` 可以为空。
- 原因：强迫失败路径给出候选会奖励无依据推荐，违反“证据不足时停止”原则。
- 结果：正常完成案例仍固定一个允许候选；失败或暂停案例要求不产生推荐和最终制品。

## D-018：checkpoint 只保存版本化业务状态

- 状态：accepted
- 日期：2026-07-29
- 决定：最小运行合同固定为 `runtime-state-v1`；Pydantic 拒绝未知字段、非法组合和越界计数，节点只返回自己负责的基础类型状态增量。
- 原因：checkpoint 应保存恢复决策所需业务事实，不应序列化进程内对象或扩大敏感数据面。
- 保存：`run_id/thread_id`、状态和当前节点、原始与确认需求、人工确认 revision、有限循环计数、证据 ID、安全错误摘要、报告 revision/hash、`artifact_id` 和幂等键。
- 不保存：编译图、SQLite 连接/checkpointer、模型客户端、工具执行器、密钥提供器、API Key、Cookie、鉴权头、连接字符串、完整供应商请求/响应或未脱敏堆栈。
- 结果：严格 msgpack checkpoint 只接收项目自有基础类型和严格合同；秘密形态错误摘要与未知敏感字段在持久化前被拒绝。

## D-019：需求暂停使用预写等待状态和 revision 绑定

- 状态：accepted
- 日期：2026-07-29
- 决定：`validate_request` 只判定缺失项；`confirm_requirements` 先写入 `NEEDS_HUMAN`、当前 revision 和请求哈希；`await_human_requirements` 再调用 LangGraph `interrupt()`。
- 原因：`interrupt()` 恢复时会从节点开头重放。暂停前先持久化等待状态，进程重启后仍能判断人工决定对应哪个请求版本。
- 路由：批准只进入确定性 `plan_research` 占位；编辑回到校验并增加 revision；拒绝和取消进入稳定终态。
- 安全：人工决定必须同时匹配 `run_id`、`thread_id`、revision 和请求哈希；旧批准不能授权编辑后的需求。
- 边界：本阶段不执行检索、模型、写作、审校、导出或其他外部副作用。

## D-020：Tool Calling 提案必须经过版本化合同和业务作用域校验

- 状态：accepted
- 日期：2026-07-29
- 决定：固定 `tool-call-v1`、三类参数合同和 `tool-result-v1`；只允许 `search_sources`、`read_source`、`calculate_comparison`。
- 校验顺序：工具名 allowlist、Pydantic Schema、已确认候选与维度、来源和章节 allowlist、调用预算、执行、标准化结果、证据作用域。
- 原因：Schema 合法不代表业务授权。合法候选 ID 仍可能超出本次人工确认范围；已知 evidence ID 仍可能来自未批准候选。
- 结果：URL、路径、命令、未知字段、越界候选、未知来源/章节、修改后的权重和越界证据均不能进入执行结果。
- 边界：当前参数由确定性测试计划提供；尚未接入模型 Tool Calling 提案。

## D-021：重试按持久化 attempt 驱动，假执行器不进入 checkpoint

- 状态：accepted
- 日期：2026-07-29
- 决定：同一规范 Tool Call 加来源快照生成稳定逻辑调用键；attempt 写入 `runtime-state-v1`。初次调用加最多 2 次重试，共 3 次尝试。
- 原因：若脚本依赖进程内游标，checkpoint 恢复后可能重复错误结果或跳过尝试；持久化 attempt 可确定性选择同一脚本步骤。
- 路由：成功停在 `EVIDENCE_READY`；瞬时错误且有预算进入 `retry_tool`；确定性错误或预算耗尽进入 `FAILED`。
- 结果：底层假工具、来源索引和脚本属于运行时依赖，不序列化；checkpoint 只保存规范调用、安全结果、attempt、错误摘要和证据 ID。
- 边界：本阶段不真实等待、不执行指数退避；未来真实适配器使用虚拟时钟测试后再启用退避。

## D-022：证据充分性由冻结规则决定，最多补检索一次

- 状态：accepted
- 日期：2026-07-29
- 决定：使用 `evidence-policy-v1` 把每个证据要求映射为一个或多个可接受 evidence ID 组合；评估器只做确定性集合判断，不调用模型。
- 语义：可接受组合为空表示当前固定快照没有证据能满足该要求；不得用相近资料、常识或模型推断补齐。
- 路由：第一轮仍有缺口进入 `EVIDENCE_NEEDS_MORE` 并执行第二个冻结调用；第一轮充足进入 `EVIDENCE_SUFFICIENT`；第二轮仍不足以 `evidence-insufficient` 进入稳定 `FAILED`。
- 持久化：checkpoint 保存策略 ID、轮次、评估结果、缺口 ID 和 evidence ID；规则对象、来源索引、评估器、工具执行器和完整响应仍由运行时注入。
- 结果：`missing-offline-proof` 与 `conflicting-cost-evidence` 均严格执行 2 次后失败，不生成报告或制品；充分案例只执行 1 次。
- 边界：当前不生成“有限结论报告”；报告写作、审校、最终人工确认和导出留给后续阶段。
