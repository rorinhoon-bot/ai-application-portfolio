# P2 产品需求文档：AI 应用技术选型研究报告

- 版本：v0.1
- 状态：accepted
- 日期：2026-07-29
- 当前阶段：需求与架构设计；不包含完整工作流实现

## 1. 问题

AI 应用团队做技术选型时，常要比较框架、模型服务、检索组件或部署方案。资料来自多份官方文档，评价维度容易变化，结论也可能缺少可回查证据。一次聊天回答不能可靠保存研究过程；普通 RAG 又通常只完成一次检索和一次回答。

本项目把研究过程编排成显式工作流：

```text
需求确认 → 规划 → 检索 → 证据检查 → 写作 → 审校 → 人工确认 → 安全导出
```

每一步有结构化状态、条件分支、失败处理和停止条件。工作流可以暂停后恢复；最终导出必须经过人工批准。

## 2. 三个候选场景

### 场景 A：AI 应用技术选型研究报告（采用）

- 目标用户：AI 应用开发团队中的技术负责人、工程师和产品负责人。
- 输入：决策问题、目标读者、2～4 个候选方案、业务约束、评价维度和允许的数据范围。候选方案缺失时，系统可提出候选，但必须在需求确认点由人批准。
- 最终输出：带执行摘要、需求复述、候选比较矩阵、逐项证据、推荐方案、风险、限制和待验证问题的 Markdown 报告。
- 工具和数据来源：固定、经批准的公开资料快照；只读 `search_sources`、`read_source` 和确定性 `calculate_comparison` 工具。首版不开放任意网页抓取。
- Human-in-the-loop：研究范围确认；最终报告批准或退回修改。未批准时不得导出最终文件。
- 可量化评估：需求覆盖率、引用绑定有效率、候选覆盖率、无证据断言率、路由正确率、重试与停止正确率、恢复一致性、重复导出次数、人工质量评分、调用次数和耗时。
- 成本、风险和复杂度：中等。固定语料能控制费用和评估；主要风险是资料过期、评价维度偏差和模型把弱证据写成强结论。通过来源版本、证据门、限制声明和人工批准降低风险。

### 场景 B：开源库升级与迁移研究报告

- 目标用户：准备升级 Python 或 AI 依赖的开发团队。
- 输入：当前版本、目标版本、项目约束、受影响 API 和候选迁移方案。
- 最终输出：破坏性变更、迁移步骤、风险清单、测试建议和回滚建议，全部绑定版本化来源。
- 工具和数据来源：官方迁移指南、changelog、API 文档固定快照；搜索、章节读取、版本差异比较工具。
- Human-in-the-loop：确认当前项目约束和受影响范围；确认迁移计划；任何写代码或改依赖操作前再次批准。
- 可量化评估：已知破坏性变更召回率、错误版本引用率、迁移步骤覆盖率、风险分类准确率、恢复与幂等测试。
- 成本、风险和复杂度：中高。技术边界清楚，但要维护多版本语料和金标准；若接入真实仓库，隐私、路径与写操作风险明显增加。

### 场景 C：AI 产品竞品与市场研究简报

- 目标用户：产品经理、创业团队和业务分析人员。
- 输入：市场问题、竞品名单、地区、时间范围和评价维度。
- 最终输出：市场概览、竞品比较、机会、风险和引用来源。
- 工具和数据来源：公开网页、公告、定价页、新闻或付费数据库；需要联网搜索、页面读取、去重和时间校验工具。
- Human-in-the-loop：批准来源范围和可能费用；确认敏感结论；批准最终发布。
- 可量化评估：来源新鲜度、事实引用覆盖率、重复来源率、竞品覆盖率、人工事实核验通过率和研究成本。
- 成本、风险和复杂度：高。信息变化快，网页许可和反爬边界复杂，部分数据付费；主观判断难建立稳定金标准，不适合作为首版。

## 3. 推荐与原因

采用场景 A。

1. 求职展示完整：能同时证明 LangGraph、Tool Calling、结构化状态、恢复、Human-in-the-loop、评估和安全边界。
2. 范围可控：只比较 2～4 个候选方案，固定报告结构和数据快照。
3. 易于离线测试：工具、模型和人工动作都可用假实现，普通测试不访问网络。
4. 可形成量化证据：不仅评价报告内容，还能测试路由、重试、停止、恢复和幂等性。
5. 与 P1 有递进关系：学习 P1 的“可信来源与程序绑定引用”思想，但 P2 保持独立环境、独立代码和独立状态模型。

## 4. 目标用户

主要用户：

- 需要为一个明确 AI 应用需求选择技术方案的工程师或技术负责人。
- 需要理解选择依据、风险和限制的产品负责人。

首版不面向：

- 要求系统自动采购、部署、修改代码或更改生产配置的用户。
- 需要实时金融、医疗、法律或机密商业研究的用户。

## 5. 输入

### 必填

- `research_question`：要做出的具体技术决策。
- `audience`：报告读者。
- `constraints`：预算、部署、隐私、时限、语言或现有技术栈约束。
- `source_policy`：允许使用的固定资料集合和版本。

### 可由系统提出、由人确认

- `candidates`：2～4 个候选方案。
- `evaluation_dimensions`：3～8 个比较维度及权重。
- `deliverable_requirements`：报告长度、格式和必须回答的问题。

输入必须通过长度、枚举、数量和结构校验。模型提出的 URL、路径、命令、工具名和工具参数都不直接信任。

## 6. 输出

### 研究草稿

结构化草稿至少包含：

1. 执行摘要。
2. 已确认需求与约束。
3. 研究方法和来源范围。
4. 候选方案比较矩阵。
5. 逐候选分析。
6. 推荐方案及适用条件。
7. 风险、限制和证据缺口。
8. 可回查引用。

### 最终制品

- 人工批准后的 Markdown 报告。
- 机器可读运行摘要：`run_id`、状态、状态图版本、来源快照版本、报告内容哈希、节点耗时、模型和工具调用次数、重试次数及人工决策记录。
- 最终路径由程序从安全制品 ID 派生，不接受模型提供的文件路径。

## 7. 功能需求

1. 使用 LangGraph 表达显式状态图。
2. 支持需求不完整、证据不足、审校失败、工具失败和人工退回的条件路由。
3. 通过结构化 Tool Calling 使用只读检索、来源读取和确定性比较工具。
4. 工具参数必须先经过 Schema、allowlist、长度、数量和权限校验。
5. 瞬时错误可有限重试；确定性输入错误不得自动重试。
6. 需求确认和最终报告确认必须支持暂停、持久化和恢复。
7. 工作流必须有成功、失败、取消、等待人工四类可观察状态。
8. 所有循环必须有明确最大次数。
9. 最终导出必须幂等；同一批准版本重复执行不能产生重复文件或不同结果。
10. 日志和持久化状态不得保存 API Key、鉴权头或完整敏感供应商响应。

## 8. 非目标

- 不默认使用多智能体、AutoGen、CrewAI 或 A2A。
- 不开放任意互联网搜索、任意 URL 抓取或付费数据源。
- 不自动修改代码、依赖、云资源、数据库或生产配置。
- 不把模型生成内容当作事实、命令、SQL、路径或写操作参数直接执行。
- 不替代最终技术负责人决策。
- 不在首版处理实时新闻、高风险医疗、法律或金融研究。
- 不公开部署。

## 9. 验收标准

### 产品和报告

- 固定成功集中的每个报告都覆盖全部必答问题和全部候选方案。
- 引用只能绑定本次已验证证据；引用绑定有效率为 `100%`。
- 固定集中的关键事实无证据断言率不高于 `10%`。
- 推荐结论必须说明适用约束、反例或证据缺口。
- 人工报告量表平均分至少 `4/5`；量表覆盖清晰度、证据充分性、比较公平性、可执行性和限制说明。

### 工作流

- 固定路由集正确进入成功、失败或人工介入路径，路由正确率至少 `90%`。
- 工具参数非法、权限越界、确定性错误和重试耗尽均安全停止，预期停止率 `100%`。
- 每个自动循环达到上限后停止，不出现无限循环。
- 从两个 Human-in-the-loop 暂停点恢复后，状态和最终结果与不中断的等价执行一致，恢复一致率 `100%`。
- 未批准的最终报告导出次数为 `0`。
- 同一批准版本执行两次，新增最终制品数量不超过 `1`，内容哈希一致。

### 工程

- P2 使用独立 `.venv`，不复用 P1 环境。
- 普通测试不访问网络、不调用真实模型、不下载数据、不产生费用。
- 固定评估集保存数据版本、工作流版本、Prompt 版本、来源快照版本和预期路径。
- 记录成功、失败和人工介入三类测试；保存失败分类和回归结果。
- README 提供新环境启动、测试、评估、安全边界和已知限制。

## 10. 固定评估方向

首个固定集计划至少 12 个案例：

- 4 个正常技术选型任务：不同候选数量和约束。
- 2 个需求不完整案例：必须暂停等待确认。
- 2 个证据不足案例：一次补检索后拒绝强结论或失败。
- 2 个工具失败案例：覆盖瞬时错误重试和确定性错误不重试。
- 1 个人工退回修改后批准案例。
- 1 个重复恢复与重复导出案例。

评估分三层：

1. 确定性单元测试：状态归并、路由、参数校验、重试、停止、持久化和幂等。
2. 固定工作流评估：使用假模型、假工具和预设人工动作，验证完整路径。
3. 真实模型评估：只有模型、调用范围和人民币预算另行批准后执行；结果不能替代离线回归。

## 11. 数据与 API 边界

- 当前阶段不下载真实研究语料，不调用真实 API。
- 首版数据默认采用经人工批准的公开官方资料固定快照，保存来源 URL、版本、许可、获取时间和内容哈希。
- 不使用付费数据源、私有仓库、用户机密文档或开放式网页搜索。
- 下载前必须提交精确来源清单、预计大小、许可、保存位置和校验方案。
- 模型调用前必须提交模型、调用次数上限、token 或费用预算、重试策略和敏感数据边界。

## 12. 已知限制

- 固定快照可复现，但不能代表实时产品状态。
- 技术比较仍受评价维度和权重影响，人工必须确认这些前提。
- 有引用不等于结论必然正确；审校和人工批准不能省略。
- 首版只证明单工作流，不证明多智能体有收益。
