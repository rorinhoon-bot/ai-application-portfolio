## 1. 数据隔离与不可作弊约束

保留 `evals/workflow-v1.json`、`evals/gold/workflow-v1-gold.json` 与原基线。新增目录建议：

```text
evals/v2/
  workflow-cases-v1.json
  content-inputs-v1.json
  gold/content-rubric-v1.json
  results/<run_id>/manifest.json
  results/<run_id>/workflow.json
  results/<run_id>/content.json
  results/<run_id>/human-review.md
```

运行器只向生产链提供需求、公开来源和配置；评估器在运行结束后读 gold。gold 存放预期事实范围、证据支持关系和评分规则，不规定模型必须输出某个候选或逐字答案。

必须有防泄漏测试：

1. 在生产模式屏蔽 `evals/gold` 与 V1 evaluation bundle 的读取；真实资料加脚本模型仍可运行。
2. 改变 gold/expected 不改变给定脚本模型下的图轨迹或报告字节，只改变评分。
3. gold 中放独有哨兵字符串，确认不进入模型请求、工具结果、Prompt 与报告。
4. 合法改写、新 claim ID、同等证据支持的另一条件推荐应通过生产结构校验；无依据但恰好等于参考答案仍失败。
5. 生产模块不得导入评估运行器；Prompt 不含 case ID 到答案的映射。冻结数据后不能根据输出改 gold 提高分数，标注错误修正须创建新版本并解释。

开发者能读到 gold 不等于没有泄漏风险；这些测试只证明运行时隔离。预留集不用于调 Prompt，若曾用于调试，降为开发集并重新建立预留集。

## 2. 工作流可靠性：离线必跑

使用脚本模型、真实解析/检索逻辑、固定公开资料测试快照、临时 SQLite、虚拟时钟和 HTTP mock。普通测试默认网络禁用；不能通过 live marker 让 autouse 网络阻断失效。真实 API 单独进程/目录和命令启用。

| 组 | 最少场景 | 关键断言 |
|---|---:|---|
| 正常与有限简报 | 3 | 完整推荐、条件推荐、缺口简报；语义状态与完成状态分开 |
| 需求与人工审批 | 5 | 缺字段、编辑、旧批准、退回、拒绝/取消；未批准不导出 |
| 工具与来源 | 5 | 正常 search/read、空结果、越界、hash 损坏、来源提示注入 |
| 模型与预算 | 7 | 结构修复、修复失败、429、401、发送后超时、缺 usage、额度耗尽 |
| 恢复与幂等 | 6 | 两个人工门重启、结果已落盘重放、UNKNOWN 暂停、发布未 checkpoint、第二进程拒绝 |

至少 26 个固定场景；分组内复合场景必须记录子断言，不以数量代替覆盖。重试边界需要零剩余额度、刚好额度、最后一次尝试的边界测试。

指标及 MVP 门槛：

- 固定场景符合预期率：通过场景/全部场景，100%。失败与取消的正确停止也算可靠性通过。
- 安全边界违规：未批准最终导出、越权工具执行、超额发送均为 0；任一非零阻止 live。
- 恢复一致率：正确恢复的指定故障点/已执行故障点，100%。同时记录真实子进程退出恢复与单进程模拟，不混写成相同强度证据。
- 同一批准制品新增数至多 1；重复恢复不新增已成功模型请求；UNKNOWN 不能静默再发。
- 事件/usage/账本可重算；缺 usage 必须 unknown。日志泄露测试使用人造秘密，不读取真实密钥。

V1 的 144 项普通测试和逐字节评估继续通过；V2 测试数量随实现自然增长，不人为追求某个 passed 数。

## 3. 内容质量：真实生成后单独评

建立 12 个真实问题：6 个开发集、6 个预留集。覆盖正常约束、约束冲突、资料不足、版本变化、偏好改变和有迷惑性表述的来源。每题有明确维度、硬约束、应寻找的证据关系；来自官方原文与实际用户需求，不从模型生成报告反推标签。

已冻结题目清单在 [`evals/v2/content-inputs-v1.json`](../../evals/v2/content-inputs-v1.json)，评分规则在 [`evals/gold/v2-content-rubric-v1.json`](../../evals/gold/v2-content-rubric-v1.json)。两者只供 D5 运行后评分；不被生产图、工具或模型 Prompt 读取。D5 模型批次结果见 [`v2-content-evaluation-2026-09-14.md`](../../evals/results/v2-content-evaluation-2026-09-14.md)，助手单人语义复核已执行；独立人工评分尚未执行。

`scripts/run_v2_content_evaluation.py` 已能逐题运行冻结输入、自动记录完成率和引用身份有效性；它把 `semantic_quality` 固定为 `N/A_REQUIRES_HUMAN_REVIEW`，不从 rubric 推导或伪造内容质量分数。live 模式还必须传入批次预算、价格卡、共享 `--total-budget-file` 与 `--total-budget-ledger`；总额文件固定为累计500分，账本内保留150分历史占用并扣减后续预留；不得通过换授权ID或目录重置额度。

人工打分使用 [`v2-content-human-review-template.md`](../../evals/results/v2-content-human-review-template.md)。模板空白不是未完成的自动结果；它保留评分者、分子、分母和分歧的真实填写位置。

本轮 D5 已有 [助手单人复核记录](../../evals/results/v2-content-assistant-review-2026-09-14.md)，不是独立人工验收。它确认 62/62 个有引用的矩阵单元受引用原文支持，同时发现 8/12 份报告把“本次已读证据的 unknown”扩大为“整个冻结快照没有证据”，其中 1 份影响条件推荐。因此 D5 内容验收目前不通过；不能用 12/12 导出或 12/12 引用身份有效替代此结论。

范围修复后的开发题回归为 1/1：新报告正确限定 unknown，未复现条件推荐；价格卡 usage 为 6 分。它只验证一个开发题，不能覆盖或替换原 6 个预留题，也不改变上述 D5 验收结论。

至少包含：同一快照下两个不同约束可合理导致不同推荐；同一候选的框架本体与附加持久化服务必须区别；找不到支持不等于不支持；旧版本事实不能被当成当前版本事实。

人工以原子事实逐条核对，不仅核对 claims 数组：摘要、矩阵、推荐理由中的事实都进入分母。条件推断单独记录前提是否充分；纯偏好或明确建议不算外部事实。

评分时必须区分两个范围：`unknown` 可以表示本次运行实际读取的证据不足；它不能断言整个 source snapshot、框架或官方文档没有该能力。若报告把前者写成后者，按范围错误记录；若该错误改变推荐，计为严重错误。

D5 复核后，生产执行器新增确定性 candidate×dimension 覆盖：真实快照的 PydanticAI recovery 单元离线固定命中 `pa-03#durable-execution`。这降低漏读风险；没有重新生成整批报告，不能回写或提高历史 D5 分数。

最新覆盖逻辑已用一个开发题 live 回归：2×3 矩阵的 6/6 单元都有受支持引用，PydanticAI recovery 实际引用 `pa-03#durable-execution`，助手复核没有范围错误。它只是开发题单样本，不能替代整批、预留题或独立人工评审，D5 内容验收继续不通过。

为防止同类错误直接导出，草稿在模型审校前新增显式整快照缺证据断言门。命中时稳定暂停为 `REPORT_SCOPE_CLAIM_INVALID`，不会产生审校调用或导出；该有限模式检查不计入内容质量分数。

| 指标 | 定义 | 初始门槛 |
|---|---|---|
| 引用身份有效率 | 指向本次已读、hash/定位正确的引用数 / 全部引用数 | 100% |
| 事实语义支持率 | 人工确认由所引原文支持的事实数 / 全部可核验事实数 | 总体 ≥90%，逐报告同时披露 |
| 严重错误数 | 捏造能力、无视硬约束、混淆关键版本而改变推荐的错误 | 0 |
| 需求覆盖率 | 有证据回答或明确标明未知的必答单元格 / 所有必答单元格 | 100% |
| 有证据回答率 | 有有效依据的回答单元格 / 所有必答单元格 | 单独报告，不能用全写未知刷覆盖率 |
| 已知缺证据处理率 | 应避免强推荐且确实未强推荐的案例 / 已知不足案例 | 100% |
| 可回答案例推荐完成率 | 有足够资料且产出受支持条件推荐的案例 / 预先标记可回答案例 | ≥80% |
| 人工质量量表 | 清晰度、依据、比较公平性、可执行性、限制说明，各 1～5 | 平均 ≥4，任一维度均值 ≥3 |

所有比例保存分子和分母；没有报告/引用时为 N/A，不记 100%。模型失败、预算中止、人工拒绝留在全部任务分母；条件化报告质量分数同时披露交付率，不能只挑成功报告。有限简报不计作成功推荐。

对修复后只需重测的冻结案例，`scripts/run_v2_content_evaluation.py --case-ids id1,id2` 按输入文件原始顺序执行，不允许和 `--limit`/`--start-index` 混用。首个 `RECOVERY_REVIEW` 或 CLI 错误会停止同一批次，保留已运行案例和账本，避免调用下一案例。

预留集全部报告由学习者逐条评分；至少一名同学独立复核 3 份（包括不足/失败案例），记录分歧、来源及最终判定。若没有第二位评审者，如实标为单人评分限制，不伪造一致率。模型裁判只作辅助，不替代人工最终验收。

## 4. 基线和成本对比

- B0：同一模型、同一快照、同一确定性检索初始证据，一次生成报告；保留结构校验/引用绑定/人工批准，无模型补检索或语义返修。
- B1：完整 V2 的有限补检索、语义审校及返修。
- 同一批题、同一模型配置/上下文上限，分别记录输入证据哈希；B1 新读证据是处理的一部分，需要报告新增数量。先比较开发集，再冻结配置评预留集。
- 建议 12 题各跑 B0/B1 一次（24 次报告运行），再对预留集中 3 题各重复一次（6 次）；总计建议 30 次，不含首次独立 smoke 的最多 3 次。重复不足以证明统计显著性，报告波动与样本量。
- 记录模型请求总次数、token、费用预留/已知/未知、主动耗时、人工等待、每份合格报告成本。失败成本计入总额。
- 若 B1 无内容或可靠性收益且明显更贵，减少模型审校轮次；不为了展示 Agent 保留无收益循环。


## 5. 结果与演示发布规则

Manifest 保存：Git HEAD/dirty 状态、图/合同版本、模型 ID及供应商返回版本（不可用则 unknown）、Prompt/Schema hash、参数、source snapshot、数据集/gold 版本、运行模式、时间、预算及依赖锁 hash。

离线脚本模式只证明可靠性；真实资料+真实模型结果才进入内容质量。真实模型响应回放可证明解析/恢复回归，不能算新一次 live 质量验证。所有 V2 分数目前为「未测」。

示例报告、失败样本和脱敏运行摘要都需人工确认后进入 Git；原始供应商响应、密钥、账本数据库不提交。开发结束更新 `README.md`、`LLH_Study.md` 和复盘，准确记录学习者参与的代码与评审，不能写成完全独立完成。
